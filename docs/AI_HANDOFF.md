# Handoff: read this first
You are continuing the build of **The Sweetest Bakery** website (repo: online-bakery).

1. Read `README.md`, `docs/BRAND.md`, `docs/ARCHITECTURE.md`.
2. Open `roadmap/ROADMAP.md`. Do **only the version marked NEXT** in its plan table (2 to 3 things). The roadmap has a table of contents and a status tracker; update both when you finish.
3. When done: add a full entry to `roadmap/BACKLOG.md` **and** a row in its contents table; mark the items DONE in `roadmap/ROADMAP.md` (plan table + owner-request tracker) and move the NEXT marker; bump `VERSION`.
4. **Never delete** anything in roadmap or backlog. Only append. If something slips, push it to a later version and note why.
5. New ideas from the owner: add to the roadmap where they fit best.
6. Keep it sleek, modern, simple. Sections over clutter. Don't over-build, the owner has limited Claude usage.
7. Business details come from `config/business.json` only.
8. Deliver the finished version as a **.zip of the whole repo (with `.git`) with your work already committed**, named `online-bakery-vN.zip`. Do not hand over a loose patch for the owner to apply (see README rule 6).
9. **Keep the offline copy in sync.** If you change `config/business.json`, `config/site-settings.json` or `src/data/products.json`, regenerate `src/js/offline-data.js` (it is a `window.SB_OFFLINE = {business, settings, products}` copy used only when the site is opened from disk via `preview.html`). From the repo root: `python3 -c "import json;r=lambda p:json.load(open(p));print('window.SB_OFFLINE = '+json.dumps({'business':r('config/business.json'),'settings':r('config/site-settings.json'),'products':r('src/data/products.json')},indent=2,ensure_ascii=False)+';')"` and keep the header comment at the top of that file.
10. **Test before you hand over.** Open `preview.html` over `file://` in a headless browser, click through every link, and make sure nothing is dead, empty or erroring (v7 did this).
11. **Follow the plan table in `roadmap/ROADMAP.md`**; it supersedes version numbers in the old notes (kept in `roadmap/ROADMAP_ARCHIVE.md`). New owner requests: add them to the tracker (section 2) and to a version in the plan, max 2 to 3 per version; anything needing logins / email / accounts goes under BACKEND. Photos and launch/hosting are deliberately LAST and only when the owner says so.
12. The cart (`js/cart.js`) and forms are WhatsApp-only by design until the backend version. Product cards use `data-add`, not a WhatsApp link. Test the cart, the Custom Order message text and the header at 320px (cart icon + menu button must share the row).
13. **Owner rules (list 13):** visitors never choose the theme (only the owner and the automatic seasons); never link to `admin.html` from a public page and keep admin sign-up closed (admins are added by an admin); Supabase is the backend (live since v10.17).
14. **Remembered customer details (v10.13)** live only in the visitor's browser (`localStorage` `sb_me`, helper `SB.me` in `store.js`): saved only on send, opt-out tick, "Forget my details". Never send them anywhere; the Privacy page (v10.18) must mention them.
15. **Admin "Remember me" (v10.14):** the login tick box keeps the admin signed in on this device for 30 days (`localStorage` `sb_keep` = `{u, exp}`, read by `me()` in `admin.js`) and remembers the username (`sb_admin_u`); Log out clears the sign-in. v10.17 replaced the local login with Supabase sign-in; the tick now decides whether the Supabase session is kept in `localStorage` (on) or `sessionStorage` (off).
16. **Menu sections (v10.15):** `categories[]` in `products.json` is the ordered list (`id`, `name`, `icon`, optional `hidden: true`). Public pages must use `shownCategories` / `shownProducts` from `SB.load()` (never raw `categories` / `products`); only the admin uses the full lists. A section can only be deleted when empty. In Admin > Menu the "Menu sections" box is open by default and the "Menu items" list is a collapsible (closed by default, v10.16). The "New" badge is `SB.isNew(p)` driven by `settings.newDays` (default 14, 0 = off).
17. **Supabase (v10.17):** URL + publishable key are in `config/business.json` (`supabase`; public by design; **never** add a secret / service_role key anywhere). Schema + locks + admin emails live in `supabase/setup.sql` (re-runnable); admins are rows in `public.admins` (by confirmed email) checked by `is_admin()`. Menu + settings are rows `products` / `settings` in `site_data`: public pages read them via `SB.dbRead` (plain fetch, falls back to the JSON files / offline copy when unreachable); only the admin writes them (`dbSave` in `admin.js`). Orders go to `orders` (public insert only, admin read/update/delete) via `SB.saveOrder`. Admin edits no longer need Publish; keep the three JSON files + `offline-data.js` only as the fallback copy (the Backup & files tab can still export them). The build sandbox has no internet: mock Supabase in tests and say so.
18. **Auth email (v10.17.1):** Supabase's built-in sender only emails the project team (about 2 an hour), so never rely on confirm / reset emails until custom SMTP is set up (planned with v10.18). Admins get logins created in the Supabase dashboard (Add user, Auto Confirm User). Keep the plain-language messages in `mailErr` / `DASH` in `admin.js`.
19. **Admin profile (v10.17.2):** table `profiles` (user_id, email, username unique case-insensitive, avatar = small JPEG data URL <= 60 KB, made by `shrink()` in `admin.js`). First sign-in shows `setupView()` until a profile exists; if the table is missing (`state.profErr`) nothing is blocked. Reuse `avatar()` / `shrink()` / `profileForm()` for customer accounts in v10.18.
20. **Customer accounts (v10.18):** `account.html` + `js/account.js` use Supabase under their own storage key `sb-customer` (never the admin's). `SB.customer()` / `SB.customerWarm()` / `SB.saveOrder` in `store.js` link an order to a signed-in customer (`orders.user_id`, only own id allowed by the insert lock). Cart orders store `details.lines = [{id, q}]` for "Order again". Customers read only their own orders and profile; admins read all; `delete_my_account()` (admins refused) strips name / phone / details from past orders. Privacy + Terms are **drafts** the owner must confirm (data region, information officer). Email confirm / reset for customers needs the custom SMTP sender (ROADMAP 1i). Keep the "a copy of your order is saved" line on Cart and Custom Order.
21. **Order tools (v10.19):** statuses are `pending / confirmed / ready / completed / cancelled` (database check constraint); `NEXT` in `admin.js` drives the one-tap button, `numbers()` computes this week / month from `state.orders` in the browser, `slip()` builds the printable slip. **"Most popular"** = `SB.popularRank()` (RPC `popular_items`, setup.sql section 7: ids + counts only, 90 days, cancelled ignored) used by `pages.js` once at least 5 items were ordered, topped up with items ticked `popular`; setting `popularAuto` (default true) switches it off. Only cart orders carry `details.lines`. Never expose names or phones through a public function. Next: v10.19.1 = thank-you page + change log.
